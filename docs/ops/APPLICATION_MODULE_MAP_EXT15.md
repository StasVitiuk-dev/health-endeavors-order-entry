# Application module map (EXT15)

Status: **CURRENT on the feature branch only** (`claude/platform-ext15-modularization-csp-2026-10-12`). Nothing here is live until Stas merges a pull request.

## 1. In plain English

The owner dashboard's program used to be one 9,500-line file (`assets/owner-login-app.js`). EXT15 moved about 2,800 lines of it into 16 smaller files in `assets/app/`, each with one job ("Tasks page", "database access", "AI agents" and so on). The code was **moved, not rewritten**: a checking tool proves that every statement of the old program still exists exactly once, unchanged, except 14 named edits listed in §5.

Why it matters: a smaller file is easier to review, a mistake in one area is less likely to break another, and each module states what it needs, so hidden connections cannot creep back in (a test fails if they do).

## 2. How the modules work

- `assets/owner-login-modules.js` is a tiny registry (`window.HE.modules`). Each module file registers itself with a name, a version number (`api: 1`) and the list of things it needs.
- The program creates the modules **once each, in a fixed order** at start-up. A module only receives what it asked for, and it gives back a frozen list of what it offers.
- Before anything else runs, the page checks that the registry and every module file loaded and have the expected version. If one is missing or out of date (for example a half-updated browser cache), the page shows a plain message ("reload the page") instead of half-working.
- Each module file is loaded with a `?v=` fingerprint, so a new version is never mixed with an old cached one. The diagnostic summary lists the program's and every module's fingerprint.
- No framework, no build step: plain files, as before.

## 4. What stayed in the program, and why

High-risk writes stay in the program file on purpose (mission rule: "high-risk writes only via façade"). They call the shared database helpers in `he-data` (guarded updates, request keys, stock functions), but their screens were **not** moved in EXT15:

| Area | Why it stayed | Largest function |
|---|---|---|
| Purchase orders (receiving stock) | stock + money; 416-line detail screen with many shared variables | `wirePoDetail` |
| Inventory and adjustments | stock writes | `loadInventory` |
| Returns and refunds-status | money + stock | `loadReturns` |
| Recalls, legal holds, FDA | compliance records | `loadRecalls` |
| Accounting / tax records | money | `loadTaxRecords` |
| Manual orders, customers, products | orders and stock | — |
| Calendar, search, Home checks | read-only, but share many mutable variables with the page | `searchEverything` |

The remaining 47 mutable top-level variables (46 shared between functions) are listed by `npm run app:graph`. Moving a mutable variable is only safe when every function that reads or writes it moves with it; the candidates tool (`node tests/tools/app-graph.js --candidates`) lists which groups are "closed" and can move next.

## 5. Deliberate edits after the move (14 + 3 small new functions)

`node tests/tools/verify-moves.js 3a40095 --styles --changed …` must list these names; anything else changed fails the proof.

| Name | Module | Why |
|---|---|---|
| `assetVersions` | he-status | diagnostic summary now shows the program, registry and every module version, and "modules N/N" |
| `loadAttentionChecks`, `loadSystemStatus`, `loadBusinessHealth` | program | read the agent switches through `agentControls()` at the moment of use (they live in `he-agents` now) |
| `getPageBadgeCount`, `searchEverything` | program | read customer questions through `inquiriesList()` |
| `ACCOUNTING_REFUND_POLICY` | he-data | typed as a string so the type check does not flag the deliberate comparison |
| `renderSidebar` | program | group colours: `data-group-color` + a checked CSS variable instead of an inline style |
| `renderActivity` | he-audit | the "details" toggle reads the computed display (the hidden state is a class now) |
| `loadSystemMode` | program | mode pill colours through a class + CSSOM instead of an inline style |
| `loadInventory` | program | product edit toggle reads the computed display |
| `agentTruth` | he-agents | **bug fix**: a switch value that is not a real on/off (`'yes'`, `1`, empty) is now "Unknown", not "Enabled" |
| `loadAI` | program | **bug fix**: if this month's AI spend cannot be read, the page shows "?" and "could not be read" instead of "$0.00 spent, $30.00 remaining" |
| `agentJobHealthHtml` | he-agents | status colour through classes instead of inline styles |
| + 3 small new functions | he-reports, he-inquiries, he-agents | `setReportHistoryView`, `inquiriesList`, `agentControls()` give the program access to state that moved |

`--styles` means: the old program is first put through the same mechanical inline-style conversion (`style="…"` → `u-…` classes, see `CSP_AND_INLINE_STYLE_REPORT_EXT15.md`), so a style change cannot hide any other change.

## 6. Checks that keep this true

| Check | Command | Fails when |
|---|---|---|
| Graph | `npm run app:modules` | a module is created twice, out of order, in a cycle, or uses a name it did not ask for |
| Move proof | `node tests/tools/verify-moves.js 3a40095 --styles --changed …` | any statement changed that is not in §5 |
| Map freshness | `node tests/tools/module-map.js --write` then `git diff` | this document's §3 differs from the code |
| Browser | `tests/specs/modules-ext15.spec.js` | a missing or broken module does not show a clear message, a module can be created twice, or versions are missing from diagnostics |
| Mutations | `tests/mutation/run-page-mutations.js` | 9 EXT15 mutants (registry twice, missing module, hidden dependency, …) are not caught |

## 7. How to add a module next time

1. `node tests/tools/app-graph.js --candidates` → pick a closed group.
2. `node tests/tools/extract-module.js <name> "<description>" <decl1,decl2,…>` → moves the code, updates the create block, `APP_MODULES` and the page's script tags.
3. `npm run app:modules`, the move proof, `node tests/tools/module-map.js --write`, then the tests.
